# Project Research Summary

**Project:** RFP Analyzer — Federal Compliance Matrix Generator
**Domain:** AI document-intelligence pipeline (GovCon proposal automation / RFP shredding)
**Researched:** 2026-07-22
**Confidence:** MEDIUM-HIGH

## Executive Summary

This is a document-AI pipeline product, not a web app with AI sprinkled on. Everyone in this class (GovDash, GovEagle, Sweetspot, Unanet ProposalAI) converges on the same loop — shred → compliance matrix → outline — and the pipeline's extraction accuracy IS the product: one missed "shall" statement makes a real proposal non-compliant, and one hallucinated page reference destroys all trust with the target audience. Experts build this as a staged, checkpointed pipeline run by an async worker: parse → section-detect → chunk → extract (map-reduce over section-aware chunks) → cross-reference → outline → judge → assemble, with every stage artifact persisted and every requirement's provenance (file, section, page, verbatim quote) carried structurally by code, never generated by the LLM.

The recommended approach: Python/FastAPI backend with a **pure pipeline library** built and validated via CLI against real RFPs *before* any web code exists, using Claude Sonnet 5 for extraction (structured outputs + citations give schema-guaranteed JSON and 1-indexed page references), pdfplumber (MIT — not AGPL PyMuPDF) for local section segmentation, and a React/Vite SPA served as static files. Deploy on Railway as web + worker + Postgres, with a Postgres-backed job queue (`FOR UPDATE SKIP LOCKED`) for v1 and files in Cloudflare R2 behind a `FileStore` interface. The market gap this project exploits is real: no competitor offers an instant self-serve demo (all are "book a demo"), none does per-requirement compliance judgment against a capabilities profile, and none fetches packages directly from SAM.gov into analysis.

Key risks, in order: silent extraction recall failure on long documents (mitigate: section-chunked map-reduce + deterministic shall/must/will keyword reconciliation + golden-set eval from day one); hallucinated references and paraphrased text (mitigate: verbatim-quote verification with string-matching, references computed from the document map); real-world document hostility — scanned SF30 amendments, CLIN tables, non-UCF solicitations (mitigate: per-page quality gates, structure detection with honest degradation); and public-demo cost blowout (mitigate: precomputed snapshot demo with zero LLM calls on the anonymous path, rate limits + spend kill-switch for live runs).

## Key Findings

### Recommended Stack

Python 3.12+ backend — the document-processing ecosystem (pdfplumber, python-docx, XlsxWriter) and first-class Anthropic SDK (`messages.parse()` with Pydantic models) decide this. Lean on Claude itself for layout-aware extraction: native PDF ingestion (32MB / 600 pages per request at 1M context) plus the Citations API's `page_location` references cover exactly what a compliance matrix needs, leaving local parsing responsible only for section-boundary detection and chunking. Avoid LangChain/LlamaIndex (fixed deterministic pipeline, not agentic retrieval), AGPL PyMuPDF (sellable-product landmine), and cloud OCR vendors (Claude covers it).

**Core technologies:**
- FastAPI 0.139 + Uvicorn: async API, Pydantic-native — schemas shared between API responses and LLM extraction
- anthropic SDK 0.118 + Claude Sonnet 5: extraction/cross-mapping/judgment; Haiku 4.5 for cheap classification passes; structured outputs GA (grammar-constrained JSON); Batch API (50% off) for precomputing demo results
- pdfplumber 0.11 (MIT) + python-docx: local section segmentation and .docx parsing; Docling (MIT) as deferred fallback for gnarly tables/OCR only if accuracy testing demands it
- PostgreSQL 16 + SQLAlchemy 2.0 + Alembic: relational core (requirements ↔ cross-refs ↔ judgments are joins); also the job queue for v1
- XlsxWriter 3.2: formatted .xlsx export (frozen panes, autofilter, conditional formatting)
- React 19 + Vite 8 + Tailwind 4 + TanStack Query: SPA served as static files by FastAPI — one web service, no CORS
- Railway: web + worker + Postgres services; Cloudflare R2 (boto3) for file storage

### Resolved Cross-File Disagreements

Two conflicts between STACK.md and ARCHITECTURE.md, resolved here:

**1. Job queue and file storage.** STACK.md recommends RQ + Redis (queue) and Cloudflare R2 (files); ARCHITECTURE.md recommends a Postgres-backed queue (`FOR UPDATE SKIP LOCKED`) and Postgres `bytea` file storage behind a `FileStore` interface. **Resolution — split the difference, each file wins where its reasoning is stronger:**
- **Queue: Postgres-backed (ARCHITECTURE.md wins).** At showcase scale with one worker, the jobs table doubles as the progress record and run history, cuts an entire Railway service and failure mode, and `SKIP LOCKED` claiming is trivial. Demo rate limiting (Redis's secondary role in STACK.md) works fine as a Postgres counter. Migration path is clean: swap the claim loop for RQ + Redis without touching pipeline code if scale ever demands it. STACK.md itself lists a Postgres-native queue as an acceptable alternative ("removes one moving part").
- **File storage: Cloudflare R2 (STACK.md wins), behind ARCHITECTURE.md's `FileStore` interface.** Blobs in Postgres bloat the database and backups; R2's free tier (10GB, zero egress) via boto3 is standard S3 code, and both web and worker can reach it (Railway volumes can't be shared across services). ARCHITECTURE.md itself flagged its bytea call as LOW-MEDIUM confidence and deferred to stack research. The interface boundary is the part that matters — keep it.
- Net deployment: **3 Railway services** (web, worker, Postgres) + R2. No Redis in v1.

**2. Parser layer.** ARCHITECTURE.md mentions a PyMuPDF fast path; STACK.md flags PyMuPDF as **AGPL-3.0** — a landmine for the sellable-product goal. **Resolution: pdfplumber (MIT) for local parsing/section detection**, Claude native PDF + citations for the layout-aware heavy lifting, and Docling (MIT) as the deferred OCR/table fallback. No PyMuPDF anywhere.

### Expected Features

The compliance matrix's shape is domain-critical: one requirement per row; verbatim text (never paraphrased); source reference with section + paragraph + page; type (L/M/C-SOW/clause/attachment); binding keyword; proposal volume mapping; F/P/N compliance level; cross-reference cells; empty owner/status columns for team workflow. Get this wrong and domain credibility dies instantly. Use industry vocabulary ("shredding").

**Must have (table stakes):**
- PDF + Word multi-document package upload (base + SF30 amendments + attachments)
- Requirement extraction with ID, verbatim text, section/page reference, binding keyword
- L/M/C-SOW type classification
- Source traceability on every row — no reference, no trust
- Formatted Excel (.xlsx primary) + CSV export matching practitioner column structure
- Proposal outline derived from Section L
- Requirements found outside L/M (attachments, PWS, Section H)

**Should have (differentiators):**
- L↔M↔C cross-mapping with gap/orphan flags — the analytical heart, lead differentiator
- Per-requirement compliance judgment (graded F/P/N + rationale + confidence) vs capabilities profile — apparently unique in the category
- SAM.gov fetch by solicitation number — no competitor feeds the shredder from SAM.gov directly
- Instant 60-second public demo (precomputed) — unique; entire category is "book a demo"
- Extraction confidence scoring / self-auditing output stats

**Defer (v2+):**
- Amendment (SF30) diffing — high value, high complexity; v1 does detection + impact flagging only
- Matrix review/edit UI — contradicts the automated thesis; Excel is the edit environment
- Proposal drafting, capture/CRM, teams/billing/SSO, non-federal formats — scope traps

### Architecture Approach

A staged, checkpointed pipeline run by an async worker; thin web layer submits jobs and polls status. The single most important boundary: **`pipeline/` is a pure library** — no HTTP, no queue imports; every stage is `f(artifact) → artifact`. This lets the whole pipeline be built and eval-validated from a CLI harness against real RFPs before any web code exists. Each stage persists its artifact to Postgres (resumability: an LLM failure at minute 6 doesn't re-pay minutes 1–5; per-stage debuggability; free progress UI). Extraction is exhaustive map-reduce over section-aware chunks carrying provenance envelopes (`{doc_id, section_path, page_start, page_end}`) — never whole-document single-pass, never RAG/embeddings. Demo mode serves a persisted snapshot with optional replay; zero LLM calls on the public path.

**Major components:**
1. Intake (upload + SAM.gov fetch, file classification) — API service
2. Pipeline library: parse → section-map → chunk → extract → cross-ref → outline → judge → assemble
3. Worker: claims jobs from Postgres queue, runs stages, checkpoints artifacts + progress
4. Matrix assembly/export: SQL join view rendered to .xlsx/.csv on demand (never stored as source of truth)
5. Demo mode: snapshot + replay, isolated from the live pipeline at runtime
6. Evals: hand-shredded ground truth + recall/precision scoring — the objective accuracy signal

### Critical Pitfalls

1. **Silent recall failure ("lost in the middle")** — single-pass whole-doc extraction drops mid-document requirements with no error. Avoid: section-chunked map-reduce + deterministic keyword sweep (shall/must/will/should) reconciled against LLM output + golden-set eval built alongside the first extraction prompt.
2. **Hallucinated references / paraphrased text** — LLMs fabricate section/page refs (11–57% citation hallucination rates). Avoid: verbatim quotes string-matched against source; section/page computed structurally from the document map + quote offsets. Must be in the *first* extraction implementation — retrofitting is a rewrite.
3. **Non-UCF solicitations** — task orders, FAR Part 12/SF 1449, instructions buried in attachments; the FAR overhaul is actively restructuring formats. Avoid: structure-detection as pipeline stage one; prompt for *roles* not literal section letters; degrade honestly ("non-standard structure — results may be incomplete").
4. **PDF parsing garbage cascades** — scanned SF30s, CLIN tables, repeated headers. Avoid: per-page text-quality gates, OCR routing, header/footer stripping; surface parsing quality in output.
5. **Amendment ignorance** — shredding a stale base solicitation creates false confidence. v1 minimum: detect SF30s, extract change statements as their own rows ("supersedes L.4.2"), flag affected requirements. Never silent-merge in v1.
6. **Demo cost/abuse blowout** — precomputed demo path (zero LLM calls), rate limits, spend kill-switch, upload validation, prompt-injection hardening (document text is data, not instructions).
7. **Overconfident output** — self-auditing matrix ("412 extracted; 396 verbatim-verified; 9 flagged") is *more* impressive to proposal professionals than pretended perfection.

## Implications for Roadmap

Research strongly converges on inside-out pipeline construction: prove parsing and extraction accuracy via CLI + evals first, wrap in web/jobs second, add showcase layers last. Phases below merge ARCHITECTURE.md's build order with PITFALLS.md's phase mapping.

### Phase 1: Parsing & Structure Foundation
**Rationale:** Everything downstream consumes ParsedDocument + section tree; federal section detection is the riskiest deterministic piece, and parsing garbage cascades through everything. Pure library + CLI harness — no web code.
**Delivers:** Domain models, PDF/Word parsing with page/heading preservation, per-page quality gates, UCF structure detection with non-UCF classification, section-aware chunking with provenance envelopes, amendment (SF30) file detection. Cost-per-run instrumentation scaffolding.
**Addresses:** Multi-doc package handling (table stakes)
**Avoids:** Pitfalls 3 (non-UCF), 4 (parsing cascade), 10 (pure-library design pre-commits to async)
**Also:** Request the SAM.gov API key now — issuance reportedly takes ~10 business days.

### Phase 2: Requirement Extraction & Grounding
**Rationale:** The product core; must be provably accurate before anything is built on it. Golden-set eval and keyword-reconciliation backstop built alongside the first prompt, not after.
**Delivers:** Map-reduce extraction over chunks (structured outputs, bounded concurrency), verbatim-quote verification with structural section/page derivation, L/M/C/clause classification (Haiku tier), binding-keyword tagging, dedupe/merge with stable requirement IDs (design for future amendment diffing), amendment change-statement extraction, recall/precision evals in CI.
**Uses:** Claude Sonnet 5 + citations, pdfplumber chunk provenance, Pydantic schemas
**Avoids:** Pitfalls 1 (missed shalls), 2 (hallucinated refs), 5 (amendment handling), 6 (confidence signals originate here)

### Phase 3: Cross-Mapping, Outline & Compliance Judgment
**Rationale:** All three operate purely on the compact extracted requirement set (cross-ref and judgment are independent of each other; can parallelize). Profile schema design must precede judgment.
**Delivers:** L↔M↔C cross-map with gap/orphan flags; Section L → proposal outline tree + requirement assignment; capabilities profile schema + fictional demo profile; batched graded judgments (Compliant/Partial/Gap/Insufficient-info) with profile-evidence citations and confidence.
**Addresses:** Both lead differentiators
**Avoids:** Pitfall 6 (graded judgments, never binary)

### Phase 4: Matrix Assembly & Export
**Rationale:** First end-to-end deliverable — full pipeline works via CLI. Cheap phase because Phases 2–3 captured the right data model (verbatim text, source doc, page, offsets).
**Delivers:** Matrix as SQL join view; formatted .xlsx (practitioner column set, frozen header, autofilter, wrapped text, summary sheet with counts/gaps/flags/amendment list, empty owner/status columns); CSV with UTF-8 BOM; formula-injection escaping.
**Avoids:** Pitfall 8 (unusable Excel) — benchmark against published GovCon matrix templates

### Phase 5: Web Service & Job Orchestration
**Rationale:** Wrap the proven library in the async shell. Standard patterns throughout.
**Delivers:** FastAPI intake/status/matrix/export endpoints; Postgres jobs table with `SKIP LOCKED` worker claim loop; stage checkpointing/resume; per-run token/cost accounting; R2 FileStore; React SPA (upload → stage progress via polling → summary-first matrix view → download); Railway deploy (web + worker + Postgres).
**Avoids:** Pitfall 10 (async from day one)

### Phase 6: Demo Mode & Public Hardening
**Rationale:** Requires a working run to snapshot; gates the public URL. This is the showcase itself.
**Delivers:** Precomputed sample-RFP snapshot (Batch API, 50% off) + optional honest replay mode; zero LLM calls on anonymous path; per-IP rate limits, upload size/page caps, daily spend kill-switch; prompt-injection hardening; retention policy note.
**Avoids:** Pitfall 7 (cost/abuse)

### Phase 7: SAM.gov Fetch
**Rationale:** Additive intake front-end to the existing upload pipeline; external-API risk isolated last; quota may be 10 requests/day, so caching discipline is mandatory and the feature must degrade gracefully to upload.
**Delivers:** Solicitation-number search → notice + amendment-notice resolution → resourceLinks attachment downloads (in worker) → same multi-file pipeline; aggressive permanent caching of every response and file.
**Avoids:** Pitfall 9 (SAM.gov assumptions), Pitfall 5 via API path (amendment-notice attachments)

### Phase Ordering Rationale

- Dependencies run bottom-up: matrix quality is capped by extraction quality, which is capped by parsing/sectioning quality — so correctness phases (1–4, CLI-verifiable and eval-driven) precede productization (5–6) and integration (7).
- Pure-library-first means the expensive, risky work is debuggable and measurable without web plumbing, and the eval harness doubles as showcase material.
- Data-model decisions that are rewrites-if-wrong (verbatim quotes + offsets, stable requirement IDs, graded judgment schema) all land in Phases 2–3, before anything consumes them.
- Demo mode last-but-one because it snapshots a real run; SAM.gov last because it's additive and externally risky — but its API key request happens in Phase 1.

### Research Flags

Phases likely needing deeper research during planning:
- **Phase 2 (Extraction):** Validate whether Citations API and structured outputs combine in a single call (STACK.md flagged unverified); extraction prompt engineering for implicit requirements; amendment change-statement semantics (PITFALLS.md explicitly flags amendment handling as the hardest open problem).
- **Phase 7 (SAM.gov):** API key tier/quota empirical confirmation, resourceLinks behavior, amendment-notice linkage — official docs are vague; secondary sources only MEDIUM confidence.
- **Phase 3 (Judgment):** Capabilities profile schema design has no established pattern (feature is apparently unique in the category); may need light research on grounding judgment against profile evidence.

Phases with standard patterns (skip research-phase):
- **Phase 4 (Export):** XlsxWriter is well-documented; column spec is fully defined in FEATURES.md.
- **Phase 5 (Web/Jobs):** FastAPI + Postgres queue + polling + Railway are thoroughly documented patterns.
- **Phase 6 (Demo):** Snapshot/replay + rate limiting are straightforward given Phase 5 infrastructure.
